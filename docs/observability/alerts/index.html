    Alerts

    Every alert Sourcegull's Prometheus rules can fire, with what to do about it. The rules are generated from crates/monitoring into deploy/docker/prometheus/sourcegull-alerts.yml (in the Compose bundle, to load into your Prometheus) and the Helm chart's PrometheusRule (metrics.prometheusRule.enabled=true); README.md shows how to set them up. See dashboards.md for the panels they watch.

    Each alert is named sourcegull_<service>_<observable> and carries the labels severity (warning: needs a look soon; critical: users are affected or will be shortly), service, owner and sourcegull_alert (the anchor below). A warning and a critical rule share a name; inhibit the warning while the critical one fires. Alertmanager routing is up to your Prometheus setup.

    #web_http_5xx_ratio

    web: share of requests answered with 5xx

    Descriptions

    • warning: web: share of requests answered with 5xx above 2% for 5m
    • critical: web: share of requests answered with 5xx above 10% for 10m

    Next steps

    • Find the failing routes: in Grafana, run sum by (route, status) (rate(sourcegull_http_requests_total{role=~"web|all",status=~"5.."}[5m])).
    • Read the web logs for error entries around that time (docker compose logs web, kubectl logs -l app.kubernetes.io/component=web). Failed responses carry an x-request-id that appears in the log lines.
    • Many 502/503 from GraphQL or search often mean Postgres or the repo nodes are unreachable: check the Postgres and repo dashboards.
    • Panel: share of requests answered with 5xx on the Sourcegull: web dashboard.

    Query

    promql
    (sum(rate(sourcegull_http_requests_total{role=~"web|all",route!~"/metrics|/healthz|/readyz",status=~"5.."}[5m])) or 0 * sum(rate(sourcegull_http_requests_total{role=~"web|all",route!~"/metrics|/healthz|/readyz"}[5m])))
/ sum(rate(sourcegull_http_requests_total{role=~"web|all",route!~"/metrics|/healthz|/readyz"}[5m]))

    Owner: platform

    #web_http_p90_latency

    web: 90th percentile request duration by route

    Descriptions

    • warning: web: 90th percentile request duration by route above 5s for 15m

    Next steps

    • Check which routes are slow on this panel; GraphQL (/.api/graphql) has its own panel below.
    • Slow GraphQL requests and searches are logged above observability.logSlowGraphQLRequests / observability.logSlowSearches and listed under Site admin > Slow requests.
    • Check Postgres (connection saturation, long transactions) and CPU usage of the web instances; add web replicas if they are CPU-bound.
    • Panel: 90th percentile request duration by route on the Sourcegull: web dashboard.

    Query

    promql
    histogram_quantile(0.9, sum by (le, route) (rate(sourcegull_http_request_duration_seconds_bucket{role=~"web|all",route!~"/metrics|/healthz|/readyz|/.api/search/stream|/.api/compute/stream|/.api/blame/.*|/.api/scip/upload|/.api/files/.*|/.executors/.*"}[5m])))

    Owner: platform

    #web_instance_up

    web: instances answering Prometheus scrapes

    Descriptions

    • critical: web: instances answering Prometheus scrapes below 1 for 5m

    1 while Prometheus can scrape the instance's internal listener (:6060), 0 when it cannot.

    Next steps

    • Check the web containers or pods (docker compose ps web, kubectl get pods -l app.kubernetes.io/component=web) and their logs for a crash or failed start.
    • A web instance refuses to start while database migrations are pending: run sourcegull migrate up (the Helm chart's migrate job does this on upgrade).
    • If the instance runs but cannot be scraped, check that Prometheus reaches port 6060 (NetworkPolicy, Compose network).
    • Panel: instances answering Prometheus scrapes on the Sourcegull: web dashboard.

    Query

    promql
    up{role=~"web|all"}

    Owner: platform

    #repo_disk_free_ratio

    repo: free disk space on the data volume

    Descriptions

    • warning: repo: free disk space on the data volume below 15% for 10m
    • critical: repo: free disk space on the data volume below 5% for 5m

    Measured by the repo node janitor (2 minutes after start, then hourly). The node pauses clones when free space is below both SOURCEGULL_REPO_PAUSE_CLONES_FREE_PERCENT (default 10%) of the volume and SOURCEGULL_REPO_PAUSE_CLONES_FREE_GIB (default 20 GiB); Site admin > Repo nodes shows the threshold.

    Next steps

    • Grow the node's volume (Helm: repo.persistence.size on a storage class that allows expansion; Compose: the repo-0-data volume's disk).
    • Or add a repo node so repositories spread over more disks (Helm: repo.replicaCount).
    • Check Site admin > Repo nodes and Repositories for unexpectedly large repositories; excluding them in the code host connection frees their space after the next sync.
    • The repo node janitor removes repositories deleted from Sourcegull and maintains the object stores; its errors appear in the repo node's logs.
    • Panel: free disk space on the data volume on the Sourcegull: repo dashboard.

    Query

    promql
    min by (instance) (sourcegull_repo_disk_free_bytes{role=~"repo|all"} / sourcegull_repo_disk_total_bytes{role=~"repo|all"})

    Owner: source

    • Find it: SELECT pid, usename, application_name, state, xact_start, query FROM pg_stat_activity WHERE xact_start IS NOT NULL ORDER BY xact_start LIMIT 5;. Sourcegull's connections name their role in application_name.
    • Long transactions block vacuum and can hold locks other queries wait on. End it with SELECT pg_terminate_backend(<pid>); if it is stuck.
    • Schema migrations run in a transaction and can legitimately take long during an upgrade.
    • Panel: age of the oldest open transaction on the Sourcegull: postgres dashboard.

    Query

    promql
    max(sourcegull_postgres_oldest_transaction_seconds)

    #postgres_pool_saturation

    postgres: share of the connection pool in use by process

    Descriptions

    • warning: postgres: share of the connection pool in use by process above 90% for 15m

    Next steps

    • Requests wait for a connection when the pool is exhausted: raise the pool size (SOURCEGULL_DB_MAX_CONNECTIONS, or SOURCEGULL_DB_WORKER_MAX_CONNECTIONS for the worker pool) if Postgres has spare connections (see connection saturation).
    • A pool that stays full while traffic is normal points to slow queries or long transactions: check the oldest transaction panel and the slow request logs.
