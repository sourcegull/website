    Sizing the Sourcegull chart

    Three presets in examples/, for installs from a team trial up to a large instance. Use the closest one as a starting point and change it once you have measured your own load.

    All numbers here are estimates. They come from the sizing rules and performance targets below, not from load tests in a cluster.

    #The rules the presets apply

    Component Rule Status
    repo node disk about 1.5 × the size of the mirrored repositories on that node (bare repos, index shards, caches) estimate
    repo node RAM about 0.5 × the indexed source on that node (the index's hot set) + 2 GiB estimate
    repo node baseline < 500 MiB RSS + mmap of the index target
    index size ≤ 0.6 × the indexed source target
    web 1 vCPU / 1 GiB per ~50 concurrent searchers; idle RSS < 150 MiB estimate / target
    worker CPU-bound on SCIP processing (≥ 100 MB/s of SCIP input per core) and searches for watches, trends and search jobs; scale on queue depth target
    PostgreSQL everything but git data and the index: metadata, queues, permissions, code graph metadata, trends series estimate

    "Indexed source" is the size of the indexed branches' files (by default the default branch of each repository), usually far smaller than the bare repositories, which carry the whole history. A rough first guess is a quarter to a fifth of the mirrored size.

    (Requests / limits: the presets set CPU requests and memory requests and limits; there are no CPU limits, so pods can use idle CPU.)

    #Notes

    • Repo nodes can grow. After repo.replicaCount changes and every repo pod runs with the new node list, about 1/N of the repositories move to their new node: copied from the old node (no load on the code host), checked, switched over, then removed from the old node after a few minutes. Searches keep working during a move; Site admin > Repo nodes shows the progress. Moves need free space on the new nodes for their share. Scaling in clones the removed pods' repositories again from the code host (their volumes are gone). Leave room for growth in the PVC size; most storage classes can expand a PVC later, which the StatefulSet's volume template cannot.
    • Memory limits of repo nodes are kept above the requests: index files are memory-mapped, and page cache use counts towards the container's memory.
    • Workers also run the leader-elected singleton tasks, so they never scale below one replica. With KEDA (worker.autoscaling.keda) the count follows the pgqueue depth: jobs queued and due, plus jobs running, over every queue the worker processes, divided by targetJobsPerReplica. trigger: prometheus reads the same depth from the sourcegull_queue_jobs gauge in Prometheus instead of querying the database (README, "Worker autoscaling"). Without KEDA, worker.autoscaling.hpa scales on CPU instead.
    • PostgreSQL: shared_buffers about a quarter of the database's memory and effective_cache_size about three quarters, as in the presets. Use connection limits that fit the web, worker and repo pod counts at their maximum replicas (each pod keeps a pool).
    • Search latency targets (end to end at the web role): indexed literal search p50 < 30 ms and p99 < 200 ms to the first result on 10 GB of source with 8 cores, warm; unindexed search of the Linux kernel at an arbitrary commit < 2 s. They assume the index's hot set fits in RAM, which is what the repo node RAM rule is for.
